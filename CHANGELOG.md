# Change Log

All notable changes to Chrona are recorded here. Entries state what actually happened; no
entry claims verification that did not occur (see `PROGRESS.md` for command-level evidence).

## 2026-10-19 — Scheduling correctness, multi-day planning, and a simulated 14-day life

Audit of the existing app, followed by focused work. Every claim below is backed by a command that
was run; the numbers come from those runs.

### Fixed (correctness)

- **The schedule ignored the user's available hours.** `ScheduleViewModel` built its horizon as
  `midnight → midnight` and never read `UserPreferences`. Someone who told Chrona they are free
  from 09:00 could have work placed at 06:00 or at 23:30. `ScheduleInput` now carries absolute
  `availabilityWindows`, `DayHorizonFactory` derives the day's bounds from preferences (including
  an overnight day, an equal start/end, and availability that does not overlap the day), and
  flexible work is confined to those windows. Fixed commitments are deliberately *not* governed by
  availability: a lecture at 09:00 is kept whatever the user says their day looks like.
  Pinned by `AvailabilitySchedulingTest` and `DayHorizonTest`.
- **`availabilityWindows` was never persisted.** `DataStorePreferencesRepository` read and wrote
  `dayStart`/`dayEnd` but silently dropped availability on both sides.
- **A failed apply lost its own explanation.** `ScheduleViewModel` set the result message and then
  refreshed, which cleared it — so a rejected apply flashed and vanished, which is the one case
  where the user most needs to read why. Refresh now happens first and the message is set after.
- **A day the user declared impossible was treated as wide open.** An empty availability list could
  not be distinguished from "no availability configured", so a simulated closed day was planned as
  if it were free. `ScheduleInput.restrictToAvailability` and `PlanningDay.isAvailable` make
  "no capacity" expressible.
- **Every simulated day's report overwrote the previous one.** `simulation_days` had a synthetic
  autoincrement primary key defaulting to 0, and Room's REPLACE strategy deletes the conflicting
  row — so a 14-day run ended up holding only day 14. The key is now `(run_id, day_offset)`.
  Found only by running the suite on a real device; pinned by
  `recording several days keeps every one of them`.
- **Two screens never loaded at all.** `TaskBrowserViewModel` and `HistoryViewModel` had no
  `init { refresh() }`, and `refreshOnEntry()` skips its first call by design, so both sat on
  "Loading…" forever. Found by opening them on the handset.
- **Today's header overflowed on a 393dp phone.** A third header action squeezed the subtitle into
  a one-word-per-line column. The action row is now horizontally scrollable. (Same fix for the
  Simulation screen's "Reset" button, which was wrapping to "Res / et".)

### Added

- `DeterministicMultiDayPlanner` — plans a whole horizon by driving the *existing* single-day
  engine forward one day at a time, so a task that cannot fit today can still land three days
  before its deadline. Reconciliation invariant (`placed ∪ unplaced` == the pool, and the two are
  disjoint) is enforced and tested.
- `domain/simulation/**` — a 14-day life: a fixed injected clock, 52 task definitions expanding to
  **142 task instances** with 58 distinct titles, a scripted lifecycle, disruption handling, and a
  replayable reset. Everything runs through the production planner, engine and status machine.
- Room schema **v4** (purely additive) plus `RoomSimulationStore`, which can only ever delete rows
  carrying the reserved simulation label and the run's own id prefix.
- `BuildDayProposalUseCase` — one place that turns stored state into a day's plan, shared by the
  Schedule screen and the task browser so the two cannot disagree.
- New surfaces: **Tasks** (searchable, filterable browser over every task, with placement or a
  stated reason for its absence), a **History** screen reading real revision and status-log rows
  instead of a permanent placeholder, and **Simulation & Tests** with counted metrics, load/reset/
  advance/run controls and a change history.
- `docs/SIMULATION_REPORT.md` and `.json`, generated by actually running the scenarios.

## 2026-10-18 — First run on real hardware (moto g54 5G, Android 15): three device-only defects fixed

The instrumentation suite had compiled since P02 but had never been executed. With a physical
`moto g54 5G` (Android 15, API 35) attached, `./gradlew :app:connectedDebugAndroidTest` ran it
for the first time: **15 tests, 9 failed**. All nine are now fixed and the suite passes on that
device. Nothing below is inferred — each defect was reproduced on the handset and re-measured
after the fix.

- Fixed (ui): `ui/board/BoardScreen.kt` — **the board could not be used at all on a phone.** The
  root `Column` held the canvas with `fillMaxSize()`, so every sibling after it (the note/thread
  selection panel, the link editor, the Refresh button) was measured at **0×0** and lay outside
  the window. Measured on device: `board_selection_panel`, `board_add_link_target`,
  `board_add_link_confirm` and `board_refresh` all reported `Rect(0,0,0,0)`. Notes could be seen
  but never selected, so nothing could be linked. The canvas/list now lives in a
  `Box(Modifier.weight(1f))`, note and thread details open as a `ModalBottomSheet` over the board
  (the panel body scrolls), and Refresh moved into the header. After the fix the same probe reports
  `selection_panel=Rect(40,1674,1040,2330)` on a 1080×2400 screen, and a link created through the
  sheet is stored as a real `DEPENDS_ON` relationship.
- Fixed (ui): `ui/board/BoardScreen.kt` — dropdown entries now carry per-item test tags
  (`board_add_link_target_item_<id>`, `board_add_link_type_item_<TYPE>`). The same words appear on
  the notes behind the sheet, so a menu entry could not be addressed unambiguously before.
- Fixed (viewmodel): `ui/board/BoardViewModel.kt` + `ui/board/BoardRoute.kt`,
  `ui/schedule/ScheduleViewModel.kt` + `ui/schedule/ScheduleRoute.kt` — both view models survive
  navigation, so a task completed on Today stayed pinned on the board until Refresh, and a schedule
  plan could be offered from a pre-change snapshot. Both now re-read on entry via
  `refreshOnEntry()`, which no-ops on the first entry so `init` remains the single first load.
- Fixed (ui): `ui/schedule/ScheduleScreen.kt` — "No day planned yet" was unreachable: the engine
  always returns a proposal, so `proposal == null` held only before the first load. The empty state
  is now judged by the world (`state.titles.isEmpty()`), which is what it always meant.
- Tests: `BoardSliceTest` cleanup now deletes relationships as well as tasks (a leaked link made
  the next test's count wrong), the link flow is driven through one helper that picks the target
  *and* the relation type (the sheet defaults to `Supports`, so the previous `DEPENDS_ON`
  assertion could never have held), and the completion assertion waits for the write instead of
  racing it. `TaskLifecycleSliceTest` matches the printed priority/status labels as substrings, as
  the card prints them on one line. `NavigationShellTest` scrolls the settings note into view and
  asserts a real settings element instead of an empty state that never existed.
- Measured (device, OPEN-007): on the moto g54 `hasSystemFeature(MICROPHONE)=true`,
  `isRecognitionAvailable=true`, `isOnDeviceRecognitionAvailable=true`, and the app's own adapter
  reports `Available` with `RECORD_AUDIO` granted — but a real session ends in
  `ERROR_LANGUAGE_UNAVAILABLE`: the `en-US` on-device pack is not installed on this handset. A
  press-and-hold in the app therefore ends in the designed plain-language failure with typing still
  reachable. No language/offline support is assumed; voice stays optional.
- Verification: `./gradlew :app:connectedDebugAndroidTest` → **15 tests, 0 failures** on
  `moto g54 5G - 15`; `./scripts/verify.sh` → PASS (318 unit tests, lint clean).
